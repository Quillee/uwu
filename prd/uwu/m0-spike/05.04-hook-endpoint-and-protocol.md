- **How Claude Code hooks work:** a PreToolUse hook is a shell command configured in the session's settings. Claude Code runs it before each tool call and feeds it a JSON payload on **stdin** — `session_id`, `tool_name` (e.g. `"Edit"`, `"Write"`), and `tool_input` (for file tools this carries `file_path`). The hook can block the call two ways: exit with code **2** and the agent sees stderr as the denial reason, or print a JSON object with `hookSpecificOutput.permissionDecision: "deny"` and `permissionDecisionReason`. The configured hook command will be a tiny client — curl or a small Go binary — that forwards stdin to your socket and relays the response. So you are building a *server* plus that *client*; the hook process Claude Code runs is the client, not the server.
- **Why a socket at all:** the guard state (repo root, guarded set) lives in the Go app's process; the hook fires in a separate shell process per tool call. The socket is the bridge (PLAN.md §4 architecture diagram, the `PreToolUse hook (local socket)` arrow).

## Contract

*(Provisional — the stub is created when this stage is scaffolded, after task 04 closes. Intended location: `spike/internal/hookserve/` or similar.)*

A server constructed with the guard's inputs, roughly:

- `New(socket config, repoRoot string, guarded []string) *Server` — the server owns the repo root and guarded set; the handler never receives them per-request.
- `Start(ctx context.Context) error` — listens on a local socket (transport is your call, Q1). Shuts down when `ctx` is cancelled.
- `Stop() error` — releases the listener and cleans up (a unix socket leaves a file behind; see hints).

The handler's job, end to end: decode the slice of the PreToolUse JSON it cares about (`tool_name`, `tool_input.file_path` — ignore the rest), map it to a `guard.ToolCall`, call `guard.Decide`, and encode the decision in the agreed response shape. Malformed payloads should produce an error response, not a crash — a panicking hook server silently un-guards the repo.

The protocol decisions themselves — transport, response shape, denial channel — are yours (see Open questions). When scaffolded, the stub will carry a `TODO(you) 05` marker and nothing in the running app calls it until this task is green.

## Hints

### Step 1

> [!hint]- Hint 1: nudge
> Don't compare the transports by familiarity — compare them by: who can connect (any local process? only processes that can read a file?), what happens after a crash (stale socket file vs. orphaned port vs. port collision with something else), how the hook command learns the address, and whether the dumbest possible client (curl in a shell hook) can speak it.

> [!hint]- Hint 2: pointer
> In Go the two options are nearly the same amount of code: `net.Listen("unix", path)` hands you a listener that `http.Serve` (or your own accept loop) runs on just as happily as a TCP one; the alternative is `net/http` on `127.0.0.1:0` and passing the chosen port to the hook command via an env var or the settings file task 06 writes. curl speaks both — `curl --unix-socket /path/to.sock http://localhost/hook -d @-` works. If you go unix: remove the socket file in `Stop`, and unlink a stale one on startup or `Listen` fails with "address already in use".

> [!hint]- Hint 3: worked example
> How the Docker CLI talks to its daemon is this exact problem solved at scale: the daemon listens on `/var/run/docker.sock` (HTTP *over* a unix socket — the two options compose), and access is scoped purely by file permissions on the socket, with no port and no token. The moment Docker exposes TCP instead, it needs TLS and client certs, because now anything that can reach the port is a caller. Map that one-to-one: your guarded-set server on a socket file inside `.uwu/` or a temp dir is scoped to your user by the filesystem; on localhost HTTP, every process on the machine can ask it for allow/deny — harmless for a spike, but the M1 design should start from least privilege.

### Step 2

> [!hint]- Hint 1: nudge
> There are two denial channels, and they live in different processes. Exit code 2 + stderr is a property of the *hook process* — your client. The JSON `permissionDecision` object is something the hook prints on *stdout*. Your server can't exit-2 at Claude Code; it can only answer the client. So the real question for the server is: what structured answer lets the client use *either* channel? Design from where the agent actually reads the denial, backwards.

> [!hint]- Hint 2: pointer
> The Claude Code hooks reference (docs: hooks — PreToolUse) specifies both ends: the stdin payload (`session_id`, `tool_name`, `tool_input`, with `file_path` inside `tool_input` for file tools) and the JSON output contract — `hookSpecificOutput` with `hookEventName: "PreToolUse"`, `permissionDecision: "allow" | "deny" | "ask"`, and `permissionDecisionReason`. In Go, decode only the slice you use: a struct with `ToolName string` tagged `json:"tool_name"` and a nested `ToolInput struct { FilePath string }` — unknown fields are ignored for free.

> [!hint]- Hint 3: worked example
> An analogous pair: a git `pre-receive` hook denies a push by exiting nonzero with the message on stderr — dead simple, but the text is unstructured and whatever relays it can mangle it. An HTTP API denies with a structured body, `{"error": {"code": "...", "message": "..."}}` — machine-readable and it survives being forwarded through layers. The hook protocol offers you both of these at once. A design that keeps both open: the server always answers structured JSON (allow/deny + reason), and the thin client either prints it as the `permissionDecision` object or downgrades it to exit-2-plus-stderr. Then Q2 becomes a one-line change in the client, and task 09 can test both channels against the same server.

## Open questions

> [!question] Q1: Unix domain socket or localhost HTTP? (the PRD's Q2)
> The hook command must reach the Go process; both transports work and both are a page of Go.
>
> - **Unix socket:** access scoped by filesystem permissions (only your user can connect), no port to collide with anything, no address discovery problem (the path is the address). Costs: the socket file needs cleanup on stop and stale-file handling on start, the client needs `curl --unix-socket` or a Go dialer, and it's not portable to Windows the same way (irrelevant for the spike).
> - **Localhost HTTP:** the simplest possible client (`curl -d @- http://127.0.0.1:PORT/hook`), but *any* local process can hit it, so it needs at least loopback-only binding and really a token to be honest about access control; and the port must be communicated to the hook command (env var or written into the hook config by task 06).
>
> **Recommendation:** unix socket, for least privilege — the thing being guarded is write access, so the guard itself should not be the openest endpoint on the machine. Decide in step 1; whatever you pick, the *why* goes in `docs/decisions/` (step 6), because M1 inherits this reasoning.

> [!question] Q2: Which denial channel does the agent read more reliably — exit code 2 + stderr, or JSON `permissionDecision`?
> The docs describe both; the spike exists because docs are not evidence. The JSON channel is more structured and can distinguish deny from ask; the exit-code channel is simpler and harder to get subtly wrong. Lean one way in the client (hint 3 for step 2 shows how to keep both open), record the lean in the decision record, and verify empirically in [[uwu/m0-spike/09.06.08-bash-probe-experiments|09 Bash probe experiments]] — the probes will show what the agent actually saw.
>
> Both Q1 and Q2 are deliberately **not asserted by the tests** until you decide; the integration test (once scaffolded) pins the deny-response *shape*, not the transport or channel choice.
