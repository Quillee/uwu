## Why this is yours

This task answers one of the three bets M0 exists to verify: can a headless Claude Code session be driven from Go through gated phases at all? The answer directly decides the [[uwu/m0-spike/prd-m0-spike|PRD]]'s CLI-subprocess vs Go-SDK criterion — if gated driving does not work, the whole agent layer changes shape. And the pause→approve→resume mechanic you build here is the kernel of the stage gate that uwu (PLAN.md §9, M3/M4) is built around. It is the most discovery-dense task in the spike, which under `own=most` means it lands in your head, not Claude's.

## Context

- The spike app lives at `spike/` (Go module `spike`, a Wails scaffold from task 03). The driver does not touch the Wails UI; it is plain Go you can exercise from a test or a small `main`.
- Task 07 (Claude-owned) will have provided a stream-json parser in the spike module — intended location `spike/internal/stream/` or similar — that turns the CLI's output lines into typed Go events. *Provisional until 07 lands; adjust to its real API.*
- The Claude Code CLI is installed (`claude` 2.1.310). `claude -p "<prompt>" --output-format stream-json --verbose` runs one non-interactive session and emits **one JSON object per line** on stdout. The types you will see: `system` (subtype `init`, carries the `session_id`), `assistant` (model turns), `user` (tool results), and a final `result` (success/error, cost, duration). `--verbose` is required for stream-json with `-p`.
- The central constraint to internalize before designing anything: **a single `-p` run is fire-and-forget.** The process works until it decides it is done, emits `result`, and exits. There is no built-in "pause here" — so gating has to be constructed. Two legitimate mechanisms:
  - **(a) Multi-turn resume.** Run phase 1 as its own `-p` process to completion, inspect the outcome, and only after approval spawn `claude -p --resume <session_id> "<next phase prompt>"`. The gate sits *between processes*; conversation state is carried by the session id.
  - **(b) Stream-json input.** Add `--input-format stream-json`, keep stdin open, and feed the next user message (as a JSON line) only after approval. The gate sits *inside one process*.
  - Which one uwu should use is an open question (Q1 below) that you answer empirically — that answer is a deliverable of this task.
- Downstream: task 09 (Bash probes) drives sessions through this driver, and the raw recordings you produce here become task 12's fixtures and the model for M1's fake `AgentDriver`. In PLAN.md terms, you are prototyping the `agent` package's `claudecode` implementation and the seam the `engine` package's stage gate will pull on.

## Contract

*Provisional — intended home `spike/internal/driver/`, final shape settled when the stage is scaffolded against 07's parser.*

A `Driver` that owns one headless session's lifecycle:

- **`Start(ctx, prompt)`** — spawn the `claude` subprocess for the first phase and begin consuming its stdout through 07's parser. Errors if the binary is missing or the process fails to start.
- **Events** — parsed events are surfaced as they arrive, on a channel the caller ranges over. The channel closes when the session ends.
- **Phase completion** — the driver reports when a phase is complete, i.e. when the `result` event arrives. However it is exposed (a field on the event, a separate signal), the caller must be able to tell "phase done, awaiting decision" apart from "still working".
- **`Approve()`** — the gate. After a phase completes, nothing continues until the caller explicitly approves; `Approve()` kicks off the next phase (a `--resume` spawn, or the next stdin message, per your Q1 decision). No approval, no progress — that asymmetry is the point.
- **`Stop()` / context cancellation** — kills the subprocess cleanly. No orphaned `claude` processes under any exit path, including mid-phase cancellation.
- **Recording tap** — every raw stream-json line is appended, unmodified, to a per-session file *before* parsing. These recordings are the input to [[uwu/m0-spike/prd-m0-spike#Tasks|12 Session fixtures recorded]], so raw bytes matter more than parsed convenience.

Error handling per house style: return wrapped errors, no panics; `context.Context` on everything long-running.

## Hints

### Step 1

> [!hint]- Hint 1: nudge
> Two questions to settle before writing code. First: if your Go program dies while `claude` is mid-session, what happens to the child — and whose job is it to make sure the answer is "it dies too"? Second: who closes stdout, and what does your reading loop see when that happens? Get the ownership story straight (who starts, who reads, who waits, in what order) and the code is short. Also: stream-json lines are JSON objects that can embed entire file contents. How long can one line get, and does your line reader care?

> [!hint]- Hint 2: pointer
> `os/exec`: `exec.CommandContext(ctx, "claude", ...)` plus `Cmd.StdoutPipe()` before `Start()`. On Go 1.20+, set `Cmd.Cancel` (what signal to send on ctx cancel) and `Cmd.WaitDelay` (grace period before the hard kill) instead of hand-rolling kill logic. Read lines with `bufio.Scanner` — but note its default max token size is 64KB, and a stream-json line carrying a big tool result will blow past that and stop the scan with `bufio.ErrTooLong`. Give it a bigger buffer via `Scanner.Buffer`, or use `bufio.Reader.ReadString('\n')`. Order matters: drain stdout fully *before* calling `Wait()`, and always check `scanner.Err()` after the loop.

> [!hint]- Hint 3: worked example
> Analogous problem — streaming `docker logs -f <container>` into a Go channel:
>
> ```go
> func streamLogs(ctx context.Context, container string) (<-chan string, error) {
>     cmd := exec.CommandContext(ctx, "docker", "logs", "-f", container)
>     cmd.Cancel = func() error { return cmd.Process.Signal(syscall.SIGTERM) }
>     cmd.WaitDelay = 5 * time.Second
>     stdout, err := cmd.StdoutPipe()
>     if err != nil { return nil, fmt.Errorf("stdout pipe: %w", err) }
>     if err := cmd.Start(); err != nil { return nil, fmt.Errorf("start: %w", err) }
>     lines := make(chan string)
>     go func() {
>         defer close(lines)
>         sc := bufio.NewScanner(stdout)
>         sc.Buffer(make([]byte, 0, 64*1024), 4*1024*1024) // long lines
>         for sc.Scan() {
>             select {
>             case lines <- sc.Text():
>             case <-ctx.Done():
>                 return
>             }
>         }
>         _ = cmd.Wait() // reap after stdout is drained
>     }()
>     return lines, nil
> }
> ```
>
> Yours differs in the details that matter: the lines go through 07's parser instead of out raw, `Wait`'s error and exit code are worth keeping, and the caller needs to learn how the session ended — not just that the channel closed.

### Step 5

> [!hint]- Hint 1: nudge
> Where is a "phase boundary" even visible in the stream? Watch a real run: which event type says "I have finished and am not sending more"? (There is exactly one good candidate.) Then: an assistant *message* ending is not the same as the *session* ending — what distinguishes them in the output? Once you know the boundary marker, the gate is just "after that marker, do nothing until told."

> [!hint]- Hint 2: pointer
> Mechanism (a): the `session_id` you captured from `system/init` in step 2, fed to a fresh `exec.Command` as `claude -p --resume <session_id> "<phase 2 prompt>" --output-format stream-json --verbose`. Each phase is steps 1–3 again with a different argv; `Approve()` just releases the spawn of the next one. Mechanism (b): one long-lived process with `--input-format stream-json`, a `Cmd.StdinPipe()` you keep open, and `Approve()` writing the next user-message JSON line; the gate is "don't write until approved", and closing stdin is how you eventually end the session. In both cases the blocking primitive on the Go side can be as dumb as receiving on an unbuffered `approve chan struct{}`.

> [!hint]- Hint 3: worked example
> Analogous problem — driving a REPL over a pipe. Gate-shaped pseudocode for `python -i`:
>
> ```go
> stdin, _ := cmd.StdinPipe()
> // phase 1
> io.WriteString(stdin, "result = expensive_step()\n")
> waitForMarker(stdout, ">>> ") // REPL prompt = "I'm done, waiting"
> // ---- the gate: nothing happens until a human says go ----
> <-approve
> // phase 2
> io.WriteString(stdin, "publish(result)\n")
> waitForMarker(stdout, ">>> ")
> ```
>
> The REPL's prompt is its phase-boundary marker; in your stream the marker is an *event type*, not a prompt string. And in mechanism (a) the same shape holds with the pipe replaced by process spawns: `waitForMarker` becomes "phase process exited with its result event", and phase 2's `WriteString` becomes the `--resume` spawn.

### Step 6

> [!hint]- Hint 1: nudge
> Enumerate the exit paths: result arrived and process exited; caller cancelled mid-phase; process crashed; parser choked. For each: does `Wait` get called exactly once, does the recording file get closed, does the events channel get closed, and is the child actually gone? The `Cmd.Cancel`/`WaitDelay` pair from step 1 covers most of this if you set it up then — this step is verifying it, including the unlovely paths.

## Open questions

> [!question] Q1: Gate mechanism — resume-per-phase or persistent stdin?
> **(a) Resume-per-phase:** each phase is a fresh `claude -p --resume <session_id>` process; the gate lives between processes and conversation state is carried by the session id. Simpler lifecycle (every phase is the same spawn/drain/wait you built in steps 1–2), crash-isolated per phase, and it maps cleanly onto M3/M4's stage model where every stage is a discrete, inspectable unit. **(b) Persistent stdin** (`--input-format stream-json`): one long-lived process, the gate is withholding the next stdin message. A true mid-session gate with no process churn and no resume-reload cost, closer to an interactive partner than a batch pipeline. **Recommendation:** try (a) first — it is simpler and matches the milestone design — but note in your decision what (b) would buy (latency, in-flight context, the possibility of interrupting *within* a phase) so M3 can revisit with data. Decided empirically in step 4; not asserted by tests until resolved.

> [!question] Q2: What exactly marks a phase boundary in the output?
> The `result` event is the obvious candidate — but verify against the real stream: does it carry a usable success/error distinction, does anything follow it, and is there any case where the session "finishes a chunk of work" without emitting one? The alternative (a sentinel string in the assistant text, e.g. prompting the model to end phases with `PHASE-DONE`) is fragile but might be needed if `result` only appears at full process exit and you choose mechanism (b). Resolve while watching real runs in steps 1 and 5; not asserted by tests until decided.
