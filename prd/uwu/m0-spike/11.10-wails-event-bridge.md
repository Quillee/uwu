## The bridge

Written for someone fluent in React but new to Wails. Read this before step 1; the steps assume it.

### Two channels, not one

A Wails app is one Go process that owns a system webview. Your React code runs in that webview, and there are exactly two ways data crosses the boundary:

**1. Bindings — request/response, frontend pulls.** Every exported method on a struct you register as a **service** (`application.NewService(&X{})` in `Options.Services`) becomes a callable TypeScript function. The binding generator (`wails3 generate bindings`, run for you by `wails3 dev` and `wails3 build` via the Taskfile's `generate:bindings` task) writes the client under `frontend/bindings/<module>/` — for this spike, `frontend/bindings/spike/greetservice.ts`. Open it: `Greet(name)` is a two-liner that calls `$Call.ByID(<hash>, name)` and returns a `CancellablePromise<string>`. Mental model: an RPC client regenerated from your Go code, like a gRPC stub — except the "wire" is an in-process message bridge, so there is no network and no server to run. One call, one response. **In M2, these are the query functions TanStack Query wraps**: `useQuery({ queryKey: ['tasks'], queryFn: TaskService.List })`, mutations call service methods and invalidate by key.

**2. Events — push, Go initiates.** Go calls `app.Event.Emit("name", data)` on the `*application.App`; any JS listener registered with `Events.On("name", cb)` (from `@wailsio/runtime`) fires. No request precedes it; Go pushes whenever it has something to say. This is the only way Go can tell the frontend about something it did not just ask for — a test line arriving, an agent turning a node green. Two v3 details: the callback receives an **event object**, and the payload is on `.data` (look at the template's `time` listener: `timeValue.data`); and `application.RegisterEvent[T]("name")` is optional but makes the generator emit a typed event, so `.data` is `T` instead of `any`. **In M2, a single events subscriber dispatches these**: domain-change events trigger Query cache invalidation (the event is a doorbell, Query refetches via a binding), while streaming output events carry their payload straight into Zustand buffers.

Why a stream cannot be a binding: a bound method call is one Promise. It resolves once, at the end, with everything — which is precisely the "dump at the end" failure this task exists to rule out. A long-running producer needs push, so the shape is: a binding *starts* the work and returns immediately; events *carry* the output.

### Where the real state libraries will hook in

PLAN.md's rule: **"if Go can reload it, TanStack Query; if it dies with the window, Zustand."** Test *results* persisted in SQLite → Go can reload them → Query, keyed, invalidated by a domain event. The raw scrolling log of a run in progress → gone when the window closes and nobody would miss it → Zustand, appended to by the events subscriber. In M0 you use **neither** — the throwaway page holds its log in plain `useState` and subscribes in a plain `useEffect`. But as you write those two pieces, name them to yourself: the `useState<string[]>` array is standing where a Zustand streaming buffer will stand, and the `RunTests()` call is standing where a Query mutation would. If you can point at each line of your throwaway page and say which M2 construct replaces it, the teaching goal of this task is met.

### The lifecycle gotcha

`Events.On` returns its own unsubscribe function: `const off = Events.On("testrun:line", cb)`. If you subscribe in a `useEffect` and do not return `off` as the cleanup, the subscription outlives the component. React 18 StrictMode (on in `frontend/src/main.tsx`) **double-mounts** every component in dev (mount → unmount → mount) exactly to expose this class of leak: a leaked subscription means two live callbacks, and every test line renders twice. **The scaffolded template has this bug** — its `time` effect calls `Events.On` and throws the return value away. It just doesn't show, because setting the same clock string twice is invisible. Appending lines is not.

The fix is the standard effect contract — `useEffect(() => { const off = Events.On(...); return off; }, [])` — the same discipline as a WebSocket or `addEventListener`.

The Go-side counterpart: events are not buffered. An `Emit` that fires before the page has subscribed is simply gone, with no error. A service method doesn't hold the `*App` by default; reach it with `application.Get()` (or keep a reference you set in `main`), and only emit after the frontend has asked for the run — which `RunTests` being called from the page guarantees.

## Contract

Provisional until task 10 lands; the event names and payload shape are yours to finalize (see Q1).

**Go side** — a new service (e.g. `TestRunService` in `spike/testrunservice.go`, registered in `main.go`'s `Services`) or a new method on the existing one:

- `RunTests()` — kicks off task 10's runner against `spike/faketarget` (expected: `internal/testrun`) in a goroutine and returns immediately. For each line the runner produces, emit an event, e.g. `application.Get().Event.Emit("testrun:line", line)`. When the stream ends, emit a completion event, e.g. `"testrun:done"`, carrying the exit status. Register both with `application.RegisterEvent[...]` if you want typed listeners. Exact payload shape is your call — see Q1.

**React side** — `spike/frontend/src/App.tsx` replaced wholesale with a throwaway log page that:

- subscribes to `testrun:line` and `testrun:done` on mount (with cleanup on unmount),
- offers a button that calls the generated `RunTests` binding,
- renders the accumulated lines as an appending log (`useState<string[]>`),
- shows a visible done state (e.g. "exit: ok" / "exit: FAIL") when `testrun:done` arrives.

No error-handling polish, no styling beyond legibility: the page is torn down in task 13. What must be right: streaming (not buffering), the done event, and clean unsubscribe.

## Hints

### Steps 1–2 (bindings)

> [!hint]- Hint 1: nudge
> What, exactly, makes a Go method visible to the frontend? It is not an annotation and not the method body — think about what `application.New` is handed and what the toolchain does with it. And once a method is visible: when does the generated TypeScript for it come into existence or change?

> [!hint]- Hint 2: pointer
> `Services: []application.Service{application.NewService(&GreetService{})}` in `spike/main.go` is the whole registration: every exported method on the service gets a client function. The generated code lives under `frontend/bindings/spike/` and is produced by the binding generator (`wails3 generate bindings`), which `wails3 dev` and `wails3 build` run through the Taskfile — never edit it by hand. For step 2's Go side: `application.Get().Event.Emit(name, data)`, called from a goroutine `RunTests` launches so the binding returns at once.

> [!hint]- Hint 3: worked example
> Analogy: gRPC codegen. There, a `.proto` service definition is the source of truth, `protoc` emits a typed client stub, and you would never hand-edit the stub — you change the proto and regenerate. Wails v3 collapses that pipeline: the Go service struct *is* the service definition, the binding generator *is* protoc, and `frontend/bindings/spike/*.ts` is the stub. Even the vocabulary matches — v3 literally calls them services. Adding `RunTests()` and letting `wails3 dev` regenerate is the equivalent of adding an rpc to the proto.

### Steps 3–5 (events)

> [!hint]- Hint 1: nudge
> Push vs pull: a bound method is one request, one response — a Promise resolves once. A test run produces output for seconds. If `RunTests` returned the output, when would the Promise resolve, and what would the page show in the meantime? That is why the binding only *starts* the run, and a different channel carries the lines. Then: what does `Events.On` return, and what is the one place React gives you to call it?

> [!hint]- Hint 2: pointer
> JS side: `Events.On(name, cb)` from `@wailsio/runtime`; its return value *is* the unsubscribe function, so `useEffect(() => Events.On("testrun:line", onLine), [])` — returning it directly — is the entire correct cleanup for one subscription; with two, capture both and return a function calling both. Remember the payload is `event.data`, not the event itself. Go side: emits are fire-and-forget and unbuffered — emitting before anyone listens loses the event silently.

> [!hint]- Hint 3: worked example
> The same shape with a WebSocket feed, where the cleanup contract is identical:
>
> ```tsx
> function Feed() {
>   const [lines, setLines] = useState<string[]>([]);
>   useEffect(() => {
>     const ws = new WebSocket("wss://example/feed");
>     ws.onmessage = (e) => setLines(prev => [...prev, e.data]);
>     return () => ws.close();           // leak this → StrictMode shows doubles
>   }, []);
>   return <pre>{lines.join("\n")}</pre>;
> }
> ```
>
> Translate: `new WebSocket` → `Events.On`, `ws.onmessage` → the callback you pass it, `ws.close()` → the function `Events.On` returned. The functional `setLines(prev => ...)` update matters in both: the callback is registered once with `[]` deps, so it closes over stale state — appending via `prev` sidesteps that.

## Open questions

> [!question] Q1: Event payload — one event per line, or batched/structured?
> Per-line (`Event.Emit("testrun:line", line)`) is simple and chatty; a structured payload (line + stream id + sequence number) costs a struct now but is what a real multi-run UI needs. v3's `RegisterEvent[T]` makes a struct payload cheap to type end to end, which tilts this a little. Recommendation: per-line string for the spike — the point is proving the channel, not designing the schema. Note in the task 13 decision record that M2 will want structure (which node, which run, ordering), so the M2 contract should not inherit the bare string.

> [!question] Q2: Should M2 events carry data, or only invalidation signals?
> PLAN.md's contract says both exist: domain-change events dispatch into the Query cache (signal → refetch via binding), while streaming output rides the event itself into Zustand (data). While building, observe which feels right for test output specifically — is a line something Go could reload (then signal + refetch is cleaner), or purely ephemeral (then carry it)? Record the impression for the M2 PRD; no code change here either way.
