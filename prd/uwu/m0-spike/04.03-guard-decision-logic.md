## Contract

The stub lives at `spike/internal/guard/guard.go` and currently panics with its `TODO(you) 04` marker. Nothing in the running app calls it until this task is green.

```go
func Decide(call ToolCall, repoRoot string, guarded []string) Decision
```

with

- `ToolCall{Tool, FilePath string}` — `Tool` is the name exactly as Claude Code reports it (`"Edit"`, `"Write"`, `"MultiEdit"`, `"NotebookEdit"`, `"Read"`, `"Bash"`, ...). `FilePath` is the target path for file tools, **absolute or relative to the repo root**; empty for tools that name no file (Bash).
- `Decision{Allow bool; Reason string}` — `Reason` explains a denial in words the agent (and a human reading the log) can act on, and **must name the offending path**. It may be empty on allow.
- `repoRoot` is the absolute path of the target repo. `guarded` holds repo-relative prefixes (single files or whole directories) owned by in-progress human tasks.

Semantics, in full:

- **Write-capable file tools** (`Edit`, `Write`, `MultiEdit`, `NotebookEdit`) are **denied** when their path lands under any guarded prefix, and allowed otherwise.
- **Read tools are always allowed.** The guard blocks writes, not reads.
- **Bash is always allowed.** This is the documented hole — task 09 probes it, M4 designs against it. The guard does not pretend to seal it.
- **An empty guarded set allows everything** (this is what ownership `none` relies on).
- **Prefix matching is path-boundary-aware:** `guarded` must match `guarded/deep/new.txt` but not `guardedextra/file.txt`.
- **`../` traversal must not escape the check:** `open/../guarded/notes.md` is a guarded path wearing a disguise.
- A path that resolves to **outside the repo** entirely is not the guard's business; it's allowed.

## Hints

### Step 1

> [!hint]- Hint 1: nudge
> Three of the test paths — `guarded/notes.md`, `/work/faketarget/guarded/notes.md`, and `open/../guarded/notes.md` — all mean the same file. Before any comparison is possible, all three have to collapse into one canonical spelling. What form would that be, and relative to what? And once you can collapse them: what does a path look like after collapsing when it was never inside the repo to begin with? That second answer is your outside-repo signal — it doesn't need to be an error.

> [!hint]- Hint 2: pointer
> Everything you need is in the standard `path/filepath` package: `Clean`, `IsAbs`, `Join`, and `Rel`. The useful shape: get every input into an absolute path first (absolute inputs are already there; relative ones get joined onto `repoRoot`, and `Join` cleans as a bonus, which is what defuses the `../` in the middle), then `filepath.Rel(repoRoot, abs)` to come back down to repo-relative. Gotchas worth knowing: `Clean` alone does not make `../x` safe — it happily keeps leading `..` segments; and `Rel` is the gift here, because when the target is outside the base it returns a path *starting with* `..`, which is exactly the signal you want, not a failure.

> [!hint]- Hint 3: worked example
> An analogous problem: a `.gitignore`-style matcher that must compare candidate paths against patterns rooted at a project dir, where candidates arrive absolute, relative, or messy:
>
> ```go
> // normalize returns p relative to root, or ok=false if p is outside root.
> func normalize(p, root string) (rel string, ok bool) {
> 	if !filepath.IsAbs(p) {
> 		p = filepath.Join(root, p) // Join also cleans "a/../b"
> 	}
> 	rel, err := filepath.Rel(root, p)
> 	if err != nil || rel == ".." || strings.HasPrefix(rel, "../") {
> 		return "", false
> 	}
> 	return rel, true
> }
> ```
>
> The ignore matcher then compares `rel` against its patterns and treats `ok=false` as "not our project, not our problem". Your guard's outside-repo case wants the same treatment. Translate, don't transplant: check what `Rel` can return on your actual inputs.

### Step 3

> [!hint]- Hint 1: nudge
> Why must `guarded/deep/new.txt` be denied while `guardedextra/file.txt` sails through? Both start with the string `guarded`. Clearly "starts with the prefix" is the wrong question — so what *is* the right one? Think about what separates one path segment from the next, and don't forget the degenerate case where the guarded entry is a single file and the path *is* the prefix, with nothing after it.

> [!hint]- Hint 2: pointer
> Two sound shapes, pick either: (a) exact match **or** prefix-plus-separator — the path equals the guarded entry, or it starts with the entry followed by a `/`; (b) compare segment-by-segment — split both on the separator and check the guarded entry's segments are a leading run of the path's. Shape (a) is three lines; just make sure the separator check comes from the boundary, not from hoping the strings line up. (Your normalized paths are the output of `filepath`, so know what separator they actually contain on your platform.)

> [!hint]- Hint 3: worked example
> The same problem shows up in HTTP routers: does the prefix route `/api` own the request path? `/api/users` yes, `/api` itself yes, `/apikeys` no:
>
> ```go
> func routeOwns(prefix, reqPath string) bool {
> 	return reqPath == prefix || strings.HasPrefix(reqPath, prefix+"/")
> }
> ```
>
> The `+"/"` is the whole trick: it turns a string-prefix check into a path-boundary check. Your guard does this once per guarded entry against the normalized repo-relative path; first hit wins and carries the entry into the deny reason.

## Open questions

> [!question] Q1: Symlinks
> A write through a symlink that *resolves* into a guarded path (say `open/link -> ../guarded`) slips past a purely lexical check. `Decide` is pure — it cannot `stat` or `EvalSymlinks` — so resolution would have to happen in the adapter (task 05, which does have I/O), or be accepted as a known gap for M0. Recommendation: document it as a gap here and revisit in M4, where detect-and-revert (git diff on guarded paths after each turn) is already the planned backstop layer and would catch exactly this. The tests deliberately do not assert either way.

> [!question] Q2: Case sensitivity
> macOS's default APFS is case-insensitive: `Guarded/notes.md` and `guarded/notes.md` are the same file on disk, but a case-sensitive string compare treats them as different, so the capitalized spelling slips past. Matching case-insensitively, on the other hand, over-blocks on Linux. Recommendation: decide and write the decision down (a one-line comment on `Decide` is enough); M0 can live with a case-sensitive compare since the spike only needs to prove the hook mechanism, and the same M4 backstop applies. The tests deliberately do not assert either way.
